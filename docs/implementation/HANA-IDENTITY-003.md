# Identity 003 — هسته بررسی امن و یک‌بارمصرف OTP

**وضعیت:** این مرحله موتور داخلی تأیید OTP را روی مدل و دیتابیس موجود می‌سازد؛ **SMS provider، API عمومی دریافت/تأیید کد، ثبت حساب یا نشست فعال نشده‌اند**. درخواست کد از وب و موبایل برای شماره معتبر مانند مرحله قبل 503 برمی‌گرداند.

## پیاده‌سازی انجام‌شده

- `OtpCodeCryptography` با `RandomNumberGenerator.GetInt32` برای تولید کد **شش‌رقمی** و `HMACSHA256` برای تهیه digest وابسته به `challengeId + normalizedPhone + code`؛ رمز HMAC باید از secrets مدیریت‌شده با حداقل **۳۲ بایت** آمده باشد و هیچ کلید یا OTP ثابت در کد تولید وارد نشده است. مقایسه با `CryptographicOperations.FixedTimeEquals` انجام می‌شود.
- `OtpChallengeVerifier` با تراکنش PostgreSQL و `SELECT ... FOR UPDATE` روی چالش معین، بررسی مالکیت شماره، زمان صدور/انقضا، مصرف قبلی و سقف **۵ تلاش ناموفق**. در رقابت دو تأیید، صرفاً یک درخواست می‌تواند چالش را مصرف کند. هر شکست در کد، حتی فرمت نامعتبر، در صورتی که چالش فعال باشد در دیتابیس ثبت می‌شود.
- نتیجه داخلی فقط `Verified` یا `Invalid` است. این نتیجه **توکن ورود یا تأیید صلاحیت حمایتی ایجاد نمی‌کند**، و پیام به کاربر نباید جزئیات اینکه «کد/تاریخ/شماره غلط بود» را برای سوءاستفاده افشا کند.
- مدل‌های `identity.accounts` و `identity.otp_challenges` از مرحله Identity 002 بدون migration جدید استفاده می‌شوند. **کد خام در دیتابیس نگهداری نمی‌شود**؛ تست‌های یکپارچه مقدار digest را در رکوردهای موقت CI می‌سازند.

## آزمون‌های این مرحله

- آزمون واحد برای تولید کد شش‌رقمی ASCII، بررسی حداقل طول secret، وابستگی digest به شماره و شناسه چالش، کلید متفاوت و عدم پذیرش digest خراب.
- آزمون یکپارچه واقعی PostgreSQL برای استفاده یک‌باره، ثبت شمارش حدس نامعتبر، مسدودشدن پس از پنج شکست، وابستگی به شماره/شناسه، انقضا/شروع اعتبار و رقابت هم‌زمان دو تأیید.
- GitHub Actions همان PostgreSQL موقت مرحله قبل را migrate می‌کند و کل suite را اجرا می‌کند؛ معیار موفقیت نتیجه ثبت‌شده در گزارش CI است. **نتیجه واقعی:** [گزارش CI برای commit `efdf61f`](https://github.com/mahdimarzooghi4-debug/henna/actions/runs/35517314296) نشان داد هر سه job بک‌اند/وب/موبایل موفق شدند؛ **۱۴ تست دامنه و ۱۱ تست زیرساخت (مجموع ۲۵ تست، بدون شکست)** پاس شدند، از جمله استفاده یک‌باره و دو تأیید هم‌زمان بر PostgreSQL.

## برای فعال‌شدن ارسال و ورود واقعی چه کم است؟

1. قرارداد و اعتبارنامه **ارائه‌دهنده واقعی پیامک** با adapter مستقل؛ تحویل معتبر/ایمن کد، سیاست retry، جلوگیری از ثبت «ارسال شد» قبل از پذیرش واقعی provider، ثبت مرجع پیام و حذف درست challenge در failure.
2. سیاست زمان اعتبار، cooldown ارسال مجدد و محدودسازی توزیع‌شده شماره/IP/دستگاه با تنظیمات قابل audit؛ `MaxFailedAttempts=5` صرفاً محدودیت هر challenge است. رمز HMAC هر محیط نباید در README، Git، client bundle یا logs درج شود.
3. API عمومی تأیید تنها پس از طراحی نشست واقعی، refresh/revoke، ثبت یا تطبیق حساب **پس از مالکیت موفق شماره**، MFA نقش حساس و تست end-to-end؛ تا آن زمان `POST /api/v1/auth/otp/request` برای شماره معتبر همچنان 503 است.
4. عدم ارائه اعتبار حمایتی/صلاحیت فروشندگی به‌دلیل ورود؛ این‌ها دامنه‌ها و فرایندهای مجزا هستند.

**مرز این مرحله:** ابزار داخلی تأیید چالش ساخته شده، اما ورود به حنا و ارسال SMS واقعی هنوز عملیاتی نیست.
