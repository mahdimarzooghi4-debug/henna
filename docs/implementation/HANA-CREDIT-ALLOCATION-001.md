# Credit Allocation 001 — مسیر عملیاتی تخصیص نیازمحور نسخهٔ ۱

## وضعیت فعلی

محاسبه‌گر قطعی نیازمحور از حالت صرفاً دامنه عبور کرده و اکنون به مرز عملیاتی
اعتبار حنا متصل است. این اتصال به معنی معتبر دانستن خودکار ورودی خانوار،
ضرایب جغرافیایی یا منبع مالی نیست؛ آن داده‌ها باید از منابع و سیاست‌های مصوب
فراهم شوند.

زنجیرهٔ فعلی:

`LINK_HOUSEHOLD → CREATE_PROGRAM → ALLOCATE_CREDIT → CreditGrant → buyer checkout`

- پیوند حساب و خانوار با شناسهٔ ثابت خانوار و مرجع مدرک ثبت می‌شود.
- برنامه اعتبار، بودجه، تاریخ انقضا، دسته‌های مجاز و در صورت نیاز سازمان را
  منجمد می‌کند.
- تخصیص فقط توسط حساب دارای مجوز `FINANCE` یا `ADMIN` انجام می‌شود.
- هر مشمول باید با همان household link ثبت‌شده تطبیق کند و یک خانوار در یک
  برنامه نمی‌تواند چند بار تخصیص بگیرد.
- محاسبه `ΣHᵢGᵢ` قطعی، نسخه‌دار و server-side است؛ مبلغ‌ها به ریال و با سقف
  بودجه برنامه ثبت می‌شوند.
- grant ایجادشده در checkout واقعی خریدار دوباره از نظر مالک، انقضا، دسته و
  مانده کنترل می‌شود.
- همه mutationها رسید idempotency پایدار، journal و audit دارند.

## سطح عملیاتی ادمین

پنل `/admin/operations` اکنون read modelهای برنامه، اعتبار و پیوند خانوار را
از backend می‌خواند و سه فرمان بالا را از BFF محدود same-origin اجرا می‌کند.
ورودی اضافه قبل از رسیدن به backend حذف/رد می‌شود و پاسخ privileged به DTO
محدود تبدیل می‌شود. پاسخ نامشخص همان کلید و بدنه را برای retry امن حفظ
می‌کند.

این UI برای ورود دادهٔ مصوب است، نه اثبات صحت داده. خصوصاً:

- صحت فایل مناطق، MPI یا هر جدول اکسل فقط پس از بررسی خود فایل منبع قابل
  تأیید است.
- `geographicFactor` و شش امتیاز خانوار از UI اختراع نمی‌شوند و باید از
  نگاشت مصوب بیایند.
- `fundingReference` اظهار مستند مسئول مجاز است و به معنی تأیید وصول وجه
  بانکی نیست.
- پژوهش ضرایب و پیشنهادهای یادگیری مسیر جداگانه دارد؛ پیشنهاد ارزیابی‌شده
  خودکار وارد production نمی‌شود و نیازمند تأیید انسانی مستقل است.

- snapshot آموزشی first-party از رخداد واقعی `ALLOCATE_CREDIT` در journal خود
  حنا، مستقیم DB→DB و بدون HTTP/Model API ثبت می‌شود.
- فرم ارزیابی منتسب انسانی فقط پژوهشی است و backend آن را از label/training
  هوش حنا حذف می‌کند.
- learner، version و candidateها متعلق به حنا هستند؛ ADR-048 هر model API
  داخلی/خارجی یا SDK ارائه‌دهندهٔ مدل را در لایهٔ یادگیری ممنوع می‌کند.

## قواعد محاسبه نسخهٔ پایه

1. امتیاز هر یک از شش شاخص فقط در بازهٔ ۰ تا ۳ پذیرفته می‌شود.
2. ضریب جغرافیایی باید مقدار مثبت و محدودشده توسط قرارداد سرور باشد.
3. محاسبه و گردکردن در backend انجام می‌شود؛ کلاینت مبلغ grant را تعیین
   نمی‌کند.
4. مجموع تخصیص از pool برنامه فراتر نمی‌رود و ماندهٔ تخصیص‌نیافته صریحاً
   گزارش می‌شود.
5. grant فقط پس از عبور از کنترل household/program ساخته می‌شود.
6. محاسبه‌گر به‌تنهایی eligibility حقوقی، وصول منبع مالی یا صحت پرونده
   خانوار را اثبات نمی‌کند.

## شواهد CI

آزمون‌های دامنه، PostgreSQL و HTTP موارد زیر را پوشش می‌دهند:

- validation امتیاز/ضریب و بودجه؛
- یکتایی خانوار در برنامه و تطابق household link؛
- مجوز FINANCE/ADMIN و بازخوانی مجوز هنگام replay؛
- idempotency و جلوگیری از اثر مالی دوباره؛
- مصرف grant در سفارش و بازگردانی همان منبع در لغو/بازپرداخت؛
- DTO/BFF و Chromium پنل عملیات ادمین با fixtureهای صرفاً CI.

این شواهد خرید یا تأمین مالی واقعی بیرونی را ثابت نمی‌کنند.

## مرز انتشار

برای انتشار نهایی همچنان ورودی‌های واقعی و مصوب خانوار/جغرافیا، سیاست مالی و
حقوقی، منبع مالی قابل reconciliation و Release Approval لازم‌اند. اتصال
بانک/PSP، پیامک و لجستیک خارج از این ماژول است و توسط اتصال‌های خارجی
جداگانه تکمیل می‌شود.
