# اتصال خرید خریدار در وب

در شاخه توسعه پیاده شده؛ هنوز ادغام یا دیپلوی نشده است. نسخه موبایل بومی و سایر پنل‌ها جزو این تغییر نیستند.

## مسیر واقعی

کاتالوگ `/` → جزئیات `/products/{id}` → افزودن کالا به سبد سرور → `/cart` → `/checkout` → دریافت پیش‌فاکتور معتبر → ثبت سفارش → `/orders/{id}`. `/orders` سفارش‌های صاحب نشست را نشان می‌دهد.

- قیمت، نام فروشگاه و موجودی از پیشنهاد منتشرشده می‌آیند؛ قیمت به رکورد هویت کاتالوگ اضافه نشده است.
- تغییر مقدار، افزایش، کاهش و حذف با نسخه سبد انجام می‌شوند. تعارض دو صفحه با پیام مشخص و دریافت تازه سبد مدیریت می‌شود. کالای از انتشار خارج‌شده همچنان قابل حذف از سبد است.
- نام کالا در سفارش جدید هنگام خرید منجمد می‌شود. خرید دوباره انتشار کالا و دسته، موجودی، قیمت و پوشش شهر نشانی را بررسی می‌کند.
- خریدار یک فروشگاه، نشانی و نوع PERSONAL/LEGAL را انتخاب می‌کند. فقط PICKUP فعال است؛ ارسال نمایشی ساخته نمی‌شود.
- نشانی جدید با فهرست مرجع استان/شهر، متن و مختصات ذخیره می‌شود. دریافت موقعیت مرورگر فقط با کلیک کاربر است. این کنترل، نقشه تعاملی OSM یا اتصال لجستیک نیست.
- پیش‌فاکتور پنج دقیقه اعتبار دارد. خرید ناقص به تصمیم مستقل KEEP/REMOVE و تأیید صریح اقلام موجود نیاز دارد.
- اعتبار حمایتی فقط برای خرید شخصی، دسته‌های مجاز و انقضای معتبر در انتخاب نمایش داده می‌شود؛ سرور هنگام خرید دوباره کنترل می‌کند. سهم نقدی به کیف پول واقعی نیاز دارد؛ در نبود درگاه، موجودی کافی شرط ثبت است.
- پاسخ نامشخص، پاسخ نامعتبر یا قطع ارتباط به معنی موفقیت نیست. در همان صفحه کلید و payload قبلی حفظ می‌شوند و retry حتی پس از پایان تایمر پیش‌فاکتور همان درخواست را بررسی می‌کند. این intent در storage مرورگر ذخیره نشده است؛ پس از reload کامل برای بررسی نتیجه باید سفارش‌های حساب را دریافت کرد.
- لغو قبل از دریافت، بازگشت به منشأ پرداخت را نمایش می‌دهد. READY_FOR_PICKUP تا تأیید واقعی خریدار، دریافت‌شده تلقی نمی‌شود.

## مرز امنیتی وب

`/api/buyer/commerce/[...path]` فقط مسیرهای مشخص خریدار را می‌پذیرد؛ پروکسی آزاد فرمان‌های مدیر نیست. token فقط از کوکی HttpOnly سمت سرور به Bearer تبدیل می‌شود. مرورگر token و raw aggregate/شناسه صاحب کیف پول/منبع بودجه را دریافت نمی‌کند. POST به Origin هم‌سایت و UUID Idempotency-Key نیاز دارد. GET عمومی پیشنهادها هیچ bearer یا cookie به API نمی‌فرستد.

ورودی تا ۶۴KB و خروجی تا ۵۱۲KB خوانده می‌شود. redirect upstream دنبال نمی‌شود. DTO نامعتبر و مبلغ خارج از محدوده عدد صحیح دقیق JavaScript با 503 رد می‌شوند؛ outage به فهرست خالی تبدیل نمی‌شود. تمام پاسخ‌ها no-store هستند.

## مبنای ظاهر

ساختار سبد از فریم‌های `715:8` و `715:35`، مقایسه از `723:2` و جزئیات/پیشنهادها از `480:2` در فایل `uREafnhmH5dDRwPraBOmuk` خوانده شد. این فریم‌ها در فایل عنوان DRAFT دارند؛ این تغییر ادعای تصویب بصری نهایی آنها را ندارد. کنترل‌های نشانی، پیش‌فاکتور، پرداخت داخلی و سفارش برای رفتار واقعی اضافه شده‌اند؛ بنابراین تطابق پیکسلی تمام صفحه با یک فریم ثابت ادعا نمی‌شود.

توکن‌های رنگ و لوگوی موجود سایت بازاستفاده شده‌اند؛ URL موقت فیگما در کد نیست. Vazirmatn با نسخه ثابت @fontsource/vazirmatn 5.3.0 و وزن‌های 400/700 در build بسته‌بندی می‌شود و به CDN فونت نیاز ندارد.

## اعتبارسنجی

- `npm run web:typecheck` و `npm run web:build`.
- `tests/web-buyer-commerce.mjs`: فیلتر DTO، مقادیر دقیق مالی، کلید retry، URLهای بازگشت امن.
- `tests/web-buyer-commerce-gateway.mjs`: Next واقعی و upstream HTTPS جداگانه CI، CSRF، cookie boundary، پاسخ نامعتبر/بزرگ، redirect و عدم نشت داده.
- `tests/web-buyer-commerce-browser.mjs`: Chromium واقعی و API doubles محدود به CI؛ افزودن، مقدار، مقایسه، تأیید سبد ناقص، اعتبار، پاسخ نامشخص و retry بعد از انقضا، لغو و تأیید دریافت، RTL موبایل، فونت و لوگو.
- آزمون PostgreSQL واقعی بک‌اند در CommerceTests؛ نسخه سبد، رد خرید کالای از انتشار خارج‌شده بدون کسر اعتبار و snapshot نام قلم نیز بررسی می‌شوند.

آزمون مرورگر از داده‌های آزمایشی جدا استفاده می‌کند و اثبات اتصال پیامک، بانک، لجستیک یا استیج واقعی نیست.
