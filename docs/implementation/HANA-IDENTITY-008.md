# Identity 008 — نشست بومی اپ خریدار با Expo SecureStore

**دامنه:** اتصال اپ خریدار به قرارداد موجود OTP و نشست API هویت؛ افزودن هیچ صفحه نهاییِ فاقد طرح مصوب فیگما یا سرویس ارسال پیامک مصنوعی در اپ/سرور در این مرحله مجاز نیست.

## پیاده‌سازی انجام‌شده

- \`apps/mobile-consumer/src/mobile-auth.ts\`: اعتبارسنجی شماره ایرانی/کد شش‌رقمی/شناسه چالش؛ فقط پاسخ \`202\` همراه UUID درست، امکان مرحله ورود کد را می‌دهد. \`POST /api/v1/auth/otp/verify\` فقط پس از **پاسخ 200 واقعی از API** با \`tokenType=Bearer\`، توکن با قالب درست، UUID حساب و زمان انقضای معتبر حداکثر ۲۴ ساعت، آن را ذخیره می‌کند. \`400/401/429/503\` یا پاسخ ناقص هرگز موفقیت نشان نمی‌دهند.
- \`App.tsx\`: صفحه ورود موجود مطابق فیگما حفظ شده؛ مرحله درج کد، پیام نشست و دکمه خروج صرفاً **کنترل فنی موقت در همان صفحه** هستند، نه تأیید بصری فریم OTP/صفحه اصلی یا طراحی نهایی جدید. ثبت فروشگاه همچنان فقط وب است.
- \`expo-secure-store\` نسخه سازگار SDK 57 و config plugin اضافه شد؛ کلید نسخه‌دار \`hana.consumer.session.v1\`، iOS Keychain با \`WHEN_UNLOCKED_THIS_DEVICE_ONLY\` و ذخیره‌سازی رمزگذاری‌شده Android پشت Keystore. bearer در React state، لاگ، Expo public env، AsyncStorage، URL یا متن UI قرار نمی‌گیرد. \`EXPO_PUBLIC_HANA_API_BASE_URL\` فقط آدرس عمومی API است.
- پس از اجرای دوباره اپ، \`GET /api/v1/auth/session\` با bearer ذخیره‌شده اجرا می‌شود؛ 200 با UUID معتبر به معنی نشست فعال، 401 به معنی ابطال/انقضا و حذف از SecureStore است. قطعی شبکه، 503، پاسخ خراب یا خطای Keystore **نشست را بدون اثبات باطل‌شدن حذف نمی‌کند**.
- خروج با \`DELETE /api/v1/auth/session\` در API انجام می‌شود؛ **فقط پس از 204 یا 401 سرور** توکن از دستگاه پاک می‌شود. قطعی/503 باعث نگهداری توکن و نمایش پیام قابل‌تلاش‌مجدد است. شکست ذخیره‌سازی توکن تازه، تلاش best-effort برای ابطال آن را انجام می‌دهد و ورود موفق اعلام نمی‌شود.
- HTTPS برای سرور عمومی اجباری است؛ فقط در حالت \`__DEV__\`، HTTP به loopback/آدرس emulator \`10.0.2.2\` پذیرفته می‌شود. برای دستگاه واقعی/production از HTTPS با گواهی معتبر استفاده شود. توکن‌های SecureStore در iOS ممکن است بعد از حذف/نصب مجدد برنامه باقی بمانند و پس از نصب مجدد فقط با API بازاعتبارسنجی می‌شوند؛ برای انتشار باید چرخه عمر نصب و backup روی دستگاه سنجیده شود.

## آزمون و محدودیت‌ها

\`tests/mobile-auth-smoke.mjs\` در job موبایل GitHub Actions با Node 22 فقط با **HTTP و SecureStore مصنوعیِ محصور در CI**، ورود ظاهراً موفق/ناموفق، 503 بدون SMS، 401، عدم حذف در قطعی، خروج سروری، شکست keystore و محافظت HTTPS را بررسی می‌کند. این تست نه ارسال SMS واقعی است، نه ورود کاربر واقعی، نه تست native روی تلفن. گیت موجود typecheck و Android export و تست‌های backend/web نیز باید سبز شوند.

**حین پیاده‌سازی، ارائه‌دهنده SMS واقعی هنوز متصل نیست و پیش‌فرض API برای شماره معتبر همچنان 503 است؛ امکان ورود عمومی واقعی فعال نیست.** مرحله بعد: تعیین فریم OTP در فیگمای مصوب، اتصال adapter واقعی پیامک با قرارداد و secrets، سپس E2E روی دستگاه/HTTPS و آمادگی عملیاتی rate limiting/proxy. این مرحله کارکرد مالی، فروشنده یا اعتبار حمایتی اضافه نکرد.
