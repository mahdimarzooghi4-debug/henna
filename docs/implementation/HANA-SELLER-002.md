# Seller 002 — آزمون مسیر واقعی ثبت پیش‌نویس و راهنمای ورود در فرم

**مسئلهٔ مرحلهٔ قبل:** Frontend 003 ذخیره در PostgreSQL و درگاه Next.js را ساخت، اما تست HTTP وب از upstream mock استفاده می‌کرد و تست Seller DB صرفاً ذخیرهٔ مستقیم را بررسی می‌کرد. اثبات اتصال واقعی `HTTP ASP.NET Core → AuthSessionService → identity.accounts → seller.registration_drafts` و جداسازی پیش‌نویس دو حساب لازم بود.

## تحویل

- تست یکپارچهٔ `SellerRegistrationApiTests` API واقعی ASP.NET Core را در WebApplicationFactory با PostgreSQL موقت CI اجرا می‌کند. دو حساب با شمارهٔ تأییدشده و نشست‌های hash‌شده **فقط در دیتابیس آزمون seed می‌شوند**؛ نه مسیر صدور توکنِ آزمایشی در API و نه SMS ساختگی در محیط کاربر اضافه شده است.
- GET/PUT بی‌نشست به 401، GET پیش‌نویسِ موجودنبوده به 404، PUT معتبر به 200 و `DRAFT`، POSTAL معیوب یا فیلد بیش‌ازحد و شمارهٔ متعلق به حساب دیگر به 400 می‌رسد. GET فقط اطلاعات صاحب نشست را بازمی‌گرداند. PUT تکراری فقط همان ردیف را تغییر می‌دهد؛ دو حساب، دو پیش‌نویس مجزا دارند. پس از ابطال نشست صاحب پیش‌نویس، GET/PUT به 401 برمی‌گردد و نشست حساب دیگر برقرار می‌ماند. no-store و عدم نشت شناسهٔ حساب هم بررسی می‌شوند.
- فرم مصوب Figma [160:77](https://www.figma.com/design/uREafnhmH5dDRwPraBOmuk/henna-platform?node-id=160-77) بدون اختراع صفحهٔ تازه، پیش از ثبت اطلاعات وضعیت ورود را بررسی می‌کند، در نبود نشست به صفحهٔ ورود **واقعی موجود** لینک می‌دهد و دکمهٔ ذخیره را در حالت بی‌ورود/درحال‌بررسی غیرفعال می‌کند. وضعیت 503 را با 404 «پیش‌نویس وجود ندارد» اشتباه نمی‌گیرد.

## محدودیت و معیار انتشار

- پیش‌نویس **فعال‌سازی فروشگاه** نیست. طراحی مراحل بعد و بررسی مدارک هنوز نیازمند فریم مصوب است.
- ارائه‌دهندهٔ SMS هنوز انتخاب و متصل نشده؛ ورود عمومی فعال نیست. حساب‌ها و نشست‌های موجود در آزمون فقط برای اثبات مسیر واقعی با دادهٔ CI هستند.
- این مرحله UI جدیدی از روی طرح ناموجود نمی‌سازد؛ صرفاً رفتار فرم موجود را کامل می‌کند. تست‌های CI جایگزین تست بصری با فونت نهایی/دستگاه واقعی یا احراز مدارک صنفی نیستند.
