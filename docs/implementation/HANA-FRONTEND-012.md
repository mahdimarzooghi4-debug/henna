# Frontend 012 — بهبود ورودی OTP در اپ مصرف‌کنندهٔ Expo

**مرجع طراحی تأییدشده:** [ورود اپ خریدار، فریم Figma `160:58`](https://www.figma.com/design/uREafnhmH5dDRwPraBOmuk/henna-platform?node-id=160-58). تغییر داخل همان کارت ورود، با logo/assets و رنگ‌های موجود حنا و بدون صفحهٔ تازه است؛ مرحلهٔ واردکردن کد یک **state فنی** در همان کارت است و هنوز فریم بصریِ مستقلِ نهاییِ تأییدشده ندارد. این کار تأیید ضمنیِ پیش‌نویس‌های خانهٔ خریدار Frontend 010 نیست.

## تغییر واقعیِ اپ

- وقتی پاسخ معتبر `202` دریافت شد و برنامه به مرحلهٔ کد رفت، فوکوس/کیبورد به TextInput کد منتقل می‌شود. اگر صدور مجدد با challenge تازه پذیرفته شد، کد قدیمی پاک می‌شود و فوکوس به همان ورودی برمی‌گردد. پس از `429`، challenge و کد قبلی فقط **در صورت معتبرماندن سمت سرور** قابل امتحان هستند؛ اثر تغییر مرحله/شناسه برای گرفتن بی‌دلیل فوکوس ندارد. نتیجهٔ نامشخص `503` یا پاسخ ناقص صدور مجدد، challenge را کنار می‌گذارد و مرحلهٔ شماره را دوباره فوکوس می‌کند.
- پیش از `verifyOtp`، کد فارسی/عربی به رقم ASCII تبدیل می‌شود. مقدار خالی، ناقص یا غیرعددی پیام مشخص **«کد تأیید باید شش رقم باشد.»** در همان کارت دارد و **اصلاً** درخواست verification به شبکه نمی‌فرستد. خطای عمومی `400` سرور برای کد شش‌رقمی واردشده همچنان با متن «کد یا اطلاعات تأیید معتبر نیست» نمایش داده می‌شود؛ محدودیت تلاش `429` و خطای شبکه با هم اشتباه گرفته نمی‌شوند.
- ورودی شماره و کد هنگام درخواست واقعی `editable=false` است. callback تغییر متن نیز با pending guard همزمان محافظت می‌شود، بنابراین شماره/کد در حال ارسال با text جدید جفت نمی‌شود. دکمهٔ اصلاح شماره هم هنگام `loading` غیرفعال است. برای کاربران screen reader، hint خطای مرتبط و accessibilityStateِ غیرفعال‌بودن روی TextInput قرار دارد.
- کد و challenge فقط در حافظهٔ همین React UI نگهداری می‌شوند؛ bearer همچنان فقط SecureStore با `WHEN_UNLOCKED_THIS_DEVICE_ONLY` است. نه ارسال پیامک ساختگی/OTP خودکار و نه localStorage، URL، log یا دادهٔ production fixture اضافه شده است. «پذیرفته‌شدن درخواست» همچنان ادعای تحویل SMS نیست.

## آزمون و مرز صحت

`tests/mobile-otp-entry-smoke.mjs` با fixture صرفاً CI: رقم‌های فارسی/عربی، کد کمتر/بیشتر از شش رقم و نویسهٔ غیرعددی، خودداری از شبکه برای کد نامعتبر و بدنهٔ دقیقِ درخواست صحیح `MobileAuthClient` را می‌آزماید. Job موبایل `expo install --check`، TypeScript و **Android Metro bundle واقعی** را نیز اجرا می‌کند؛ تست‌های قبلی امنیت نشست و OTP، در کنار تست‌های وب و backend/PostgreSQL، برقرارند. این CI **آزمون UI روی شبیه‌ساز Android/iOS نیست**؛ فوکوس native و کیبورد باید در تست دستگاه واقعی هم بررسی شوند.

**مرز محصول:** بدون provider SMS تولیدی، درخواست کد ممکن است `503` بگیرد و ورود واقعی فعال نشده است. صفحات پیشنهادی خانهٔ خریدار همچنان NOT APPROVED؛ این PR نه خانهٔ خریدار را منتشر می‌کند، نه دسته/کالای نمونه، قیمت، فروشندهٔ فعال، سبد یا checkout می‌سازد.
