## پیشنهادِ قابل بررسی، نه قرارداد محصول

طرح پیشنهادی شش بخش پرسشی دارد:
۱. نوع متقاضی (حقیقی/حقوقی)؛ ۲. زمینهٔ اصلی فعالیت که در صورت تصویب، گزینه‌های آن تنها از دسته‌های **واقعاً منتشرشدهٔ API کاتالوگ** می‌آیند؛ ۳. ماهیت فعالیت (کالا/خدمت/هر دو)؛ ۴. شرح کوتاه فعالیت؛ ۵. عنوان حقوقی به‌صورت مشروط؛ ۶. اطلاعات صنفی به‌صورت مشروط.

**نوع کنترل، فیلدهای الزامی، تفکیک شخص حقیقی و حقوقی، نوع و فرمت مدارک/شناسه‌ها، احراز مجاز و چرخهٔ بازبینی هنوز باید به‌صورت مستقل تصویب شوند.** فریم‌ها سیاست اجباری یا تصمیم حقوقی جعل نمی‌کنند. «ذخیرهٔ پیش‌نویس» نباید وضعیت فروشنده را `ACTIVE` کند؛ مراحل محدوده فعالیت، مدارک و بررسی نهایی جدا باقی می‌مانند.

## مرز پیاده‌سازی و آزمون

هیچ فایل shipping وب/Expo، API، migration، seed، قیمت، موجودی، شهر فعال، checkout یا قابلیت خرید در Frontend 025 تغییر نکرده است. مرحلهٔ اول همچنان فقط پیش‌نویس نسخه‌دار شش فیلد خود را در PostgreSQL نگه می‌دارد؛ فریم‌های این مرحله در اپ قابل استفاده نیستند و فرم جدید/endpoint برای آن‌ها ساخته نشده است.

CI کامل `main` پس از squash merge اصلاح native iOS در [run 35867009085](https://github.com/mahdimarzooghi4-debug/henna/actions/runs/35867009085) برای `c475c600a4e4fcebec5816f8607843dfac1643b6` در پنج job backend/web/mobile/android-native-links/ios-native-links موفق شد. این فقط خط مبناست، نه پذیرش طرح جدید. برای این تغییر **طراحی/سندمحور** آزمون runtime جدیدی اضافه نشده؛ CI PR و CI پس از squash merge باید باز هم بررسی شوند.
