# Catalog 004 — ورود و بازبینی محتوای واقعی توسط اپراتور

## مسئله و تحویل

Catalog 001 API خواندن دارد و Catalog 002/003 مشتریان وب و Expo به آن دسترسی دارند، اما دادهٔ محصول در shipping عمداً نمونه‌سازی نشده است. برای واردکردن محتوای واقعی بدون اختراع پنل ادمین فاقد طرح مصوب، یک مسیر **غیر HTTP، صریح و اپراتوری** ساخته شد.

- فرمان `--catalog-preview /absolute/path/reviewed.json` دسته و محصول جدید/تغییریافته را پس از اعتبارسنجی و خواندن PostgreSQL می‌شمارد، **بدون نوشتن در DB**.
- فرمان جداگانهٔ `--catalog-apply /absolute/path/reviewed.json` همان محتوای بررسی‌شده را در یک تراکنش PostgreSQL وارد یا با ID ثابت اصلاح می‌کند. import تکراریِ بی‌تغییر رکورد تکراری نمی‌سازد.
- ورودی باید دو آرایهٔ `categories` و `products` داشته باشد؛ حداکثر ۱۰۰۰ ردیف از هر نوع و حداکثر ۱ MiB. Category: `id` (UUID)، `name`، `slug` (حروف کوچک لاتین/رقم/خط‌تیره)، `state` (`DRAFT` یا `PUBLISHED`). Product: `id`، `categoryId`، `name`، `kind` (`GOOD` یا `SERVICE`)، `description` (متن یا null)، `state`. **همهٔ وضعیت‌ها باید صریح تعیین شوند** و هیچ محصولی به‌طور پیش‌فرض منتشر نمی‌شود.
- شناسه/slug تکراری، دستهٔ ناموجود، تغییر نوع هویتی یک محصول موجود، فیلد اضافه مثل قیمت و موجودی، نام/دادهٔ نامعتبر و SQL schema قدیمی خطا می‌گیرند. اعتبارسنجی پیش از تغییر رکوردهاست، ورود با قفل جدول و تراکنش اتمیک انجام می‌شود و شکست، تغییر جزئی باقی نمی‌گذارد.
- عدم حضور یک ID در فایل **حذف یا لغو انتشار نمی‌کند**؛ فقط `state: "DRAFT"` صریح یک محتوای قبلاً منتشرشده را از خروجی عمومی مخفی می‌کند و `PUBLISHED` بعدی قابل بازگرداندن است. دستهٔ DRAFT، همه محصولات آن را از API عمومی مخفی می‌کند، بدون پاک‌کردن آن‌ها.
- command فقط با connection string بیرونی، migration اعمال‌شده و مسیر فایل مطلق اجرا می‌شود. **هیچ HTTP POST/PUT/PATCH برای تغییر وضعیت Catalog وجود ندارد.** این ابزار جایگزین پنل ادمینِ نقش‌محور یا فرایند تأیید محتوایی نیست؛ دسترسی اجرای آن باید به اپراتور مجاز و فایل تأییدشده محدود شود.

## مثال قالب (راهنمای ساخت؛ خود فایل نمونهٔ محتوای واقعی نیست)

```json
{
  "categories": [
    {
      "id": "2fd59aad-5834-4717-9462-c5e520dd7a31",
      "name": "نام دستهٔ تأییدشده",
      "slug": "approved-category",
      "state": "DRAFT"
    }
  ],
  "products": [
    {
      "id": "40a9a026-f3f8-4366-b164-d43b52b641be",
      "categoryId": "2fd59aad-5834-4717-9462-c5e520dd7a31",
      "name": "نام کالای بررسی‌شده",
      "kind": "GOOD",
      "description": null,
      "state": "DRAFT"
    }
  ]
}
```

برای اجرای واقعی از secret دیتابیس در محیط استفاده کنید و ابتدا `--apply-migrations` را جداگانه اجرا کنید؛ سپس پیش‌نمایش بگیرید و پس از تأیید اپراتور، فرمان `--catalog-apply` را روی همان نسخهٔ فایل اجرا کنید. پیش‌نمایش و اجرای جداگانه برابری محتوای فایل را تضمین نمی‌کند؛ فرایند انتشار باید hash فایل، مسئول تأیید و دسترسی اجرا را کنترل کند. بدون این فرایند، ابزار نباید در production خودکار فراخوانی شود.

## آزمون و محدودیت

تست CI روی PostgreSQL موقت و API واقعی، dry-run بدون تغییر، اعمال اتمیک، idempotency، انتشار/لغو و بازیابی، رد kind متغیر/slug متداخل/فیلد اضافه و عدم حذف خودکار را می‌سنجد. اجرای خود فرمان‌های `--catalog-preview` و `--catalog-apply` نیز با فایل موقت CI آزموده می‌شود؛ اجرای دوبارهٔ همان فایل نباید مورد جدید بسازد. دادهٔ CI در پایان پاک می‌شود؛ هیچ seed عمومی در startup یا اپ‌ها اضافه نشده است.

**هنوز این‌ها انجام نشده‌اند:** انتخاب/بارگذاری محتوای حقیقی شهر اول، هویت و مجوز ادمین/ویرایشگر، ممیزی مجوز انتشار و پنل طراحی‌شدهٔ ادمین، اتصال پیشنهاد فروشنده، قیمت/موجودی/شهر، UI خرید فیگما و SMS واقعی. این مرحله تنها روش کنترل‌شدهٔ ورود هویت کاتالوگ به DB را ایجاد می‌کند.
