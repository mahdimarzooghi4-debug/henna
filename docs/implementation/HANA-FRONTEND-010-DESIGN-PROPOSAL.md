## قرارداد موجود که طرح را محدود می‌کند

اکنون Next BFF به صورت عمومی `GET /api/catalog/categories`، `GET /api/catalog/products?page=<n>&pageSize=<n>&categoryId=<uuid>&search=<text>` و `GET /api/catalog/products/{id}` را عرضه می‌کند. قرارداد JSONِ public category فقط `id/name/slug` و product فقط `id/categoryId/name/kind/description` است؛ فهرست صفحه‌بندی `items/page/pageSize/total` برمی‌گرداند. `kind` فقط `GOOD|SERVICE` است. `search` حداکثر ۸۰ کاراکتر، `pageSize` حداکثر ۵۰ و پیش‌فرض ۲۰ است. دادهٔ مرجع واقعیِ منتشرشده هنوز تأمین نشده است. این UI پیشنهادی نباید هرگز قیمت، موجودی، فروشندهٔ فعال، پوشش شهر، زمان ارسال، سبد خرید یا checkout را از این قرارداد استنباط کند.

**تفاوت وضعیت‌ها:** `200 items:[]` برابر با نبود محتوای قابل نمایش است، ولی `503`، خطای دریافت یا پاسخ نامعتبر باید پیام «دریافت داده تأیید نشد / تلاش دوباره» بدهد، نه همان کارت «محتوا نداریم». فهرست دارای داده فقط پس از پاسخ معتبر به‌روزرسانی می‌شود. جست‌وجو و فیلتر باید `page=1` را ریست کنند؛ کلیک روی دسته تنها UUID واقعی را ارسال می‌کند؛ نداشتن دستهٔ منتخب باید فیلتر را حذف کند. حداقل یک مسیر قابل‌دسترس به ورود موجود باید حفظ شود. هیچ data fallback، شناسهٔ hard-coded یا mock در shipping UI مجاز نیست.

## تصمیمات طراحی لازم پیش از پیاده‌سازی

تأیید صریح این چهار پیش‌نویس یا درخواست اصلاح آن‌ها لازم است؛ به‌خصوص: عنوان و محل جست‌وجو، چیپ دسته‌ها، کارت متنی کالا بدون عکس/قیمت، نحوهٔ نمایش دو وضعیت `empty` و `unavailable` و چینش موبایل. فعلاً هیچ فریم مصوب برای جزئیات کالا، انتخاب شهر خریدار، آدرس، سبد و پرداخت وجود ندارد. فریم‌های قدیمی `160:40` (وب ورود)، `160:58` (موبایل ورود) و `160:77` (وب مرحلهٔ اول فروشنده) بدون تغییر باقی ماندند.

**توضیح تحویل:** این مرحله طراحی فریم‌های جدید و تثبیت قرارداد اجرای بعدی است، نه PR پیاده‌سازی صفحهٔ خانه. پس از تأیید، مرحلهٔ بعد باید نمای وب واقعیِ public/empty/error/search/filter/pagination را روی BFF موجود بسازد و سپس UI خریدار موبایل را بر اساس همان طرحِ تأییدشده پیاده‌سازی کند. انتشار خرید همچنان به خدمات تجاری، پرداخت، لجستیک و آمادگی مستقلِ شهر نیاز دارد.
