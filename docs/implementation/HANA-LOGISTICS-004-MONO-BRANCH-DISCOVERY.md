# HANA-LOGISTICS-004 — کشف شعبه‌های مونو

**مرحله:** آماده‌سازی فنی اتصال حنا و مونو  
**وضعیت:** کلاینت فقط‌خواندنی شعبه‌ها پیاده‌سازی و در CI بررسی شده است؛ نگاشت عملیاتی فروشنده به شعبه هنوز دادهٔ تأییدشده می‌خواهد.

## قرارداد فنی

- حنا از backend خود با `GET /v1/branches` و scope لازم `branches.read` شعبه‌های متعلق به کلید مشتری را می‌خواند.
- شناسه‌ها، مختصات، نام و وضعیت پاسخ قبل از تحویل به فراخواننده اعتبارسنجی می‌شوند؛ پاسخ بزرگ یا تکراری رد می‌شود.
- پاسخ در این مرحله ذخیره نمی‌شود و هیچ شناسهٔ شعبه‌ای خودکار به فروشندهٔ حنا نسبت داده نمی‌شود.
- درخواست فهرست شعبه فقط‌خواندنی است و کلید Mono در سمت سرور می‌ماند.

## آنچه برای فعال‌سازی لازم است

- کلید آزمایشی Mono با scope `branches.read` و نشانی sandbox معتبر.
- تصمیم عملیاتی برای اینکه هر فروشنده یا شعبهٔ حنا به کدام شعبهٔ مونو متصل است.
- پس از دریافت نگاشت تأییدشده، مرحلهٔ بعد باید ذخیرهٔ نسخه‌دار نگاشت و کنترل دسترسی تغییر آن باشد.

## آزمون

تست‌های transport مسیر، متد GET، احراز هویت، نبودن `Idempotency-Key`، شکل پاسخ، شناسهٔ نامعتبر و شعبه‌های تکراری را بررسی می‌کنند. این تست‌ها با HTTP handler شبیه‌سازی‌شده‌اند و اتصال sandbox را ثابت نمی‌کنند.

## منبع قرارداد

قرارداد B2B v1 مونو: [PR #247](https://github.com/mahdimarzooghi4-debug/mono-logistic/pull/247) (پیش‌نویس؛ host و credential sandbox هنوز فراهم نشده‌اند).

## تکمیل مرحلهٔ بعد

PR بعدی نگاشت نسخه‌دار seller-to-branch را از مسیر ادمین پیاده می‌کند. انتخاب فقط وقتی ذخیره می‌شود که فروشنده در حنا فعال و بدون تعلیق باشد و شعبه از API کلاینت Mono با وضعیت `ACTIVE` برگردد. تا زمانی که اپراتور نگاشتی ثبت نکند، مقدار پیش‌فرض یا استنتاج خودکار وجود ندارد.
