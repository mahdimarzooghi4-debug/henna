# Identity 009 — محدودسازی توزیع‌شدهٔ درخواست و تأیید OTP در PostgreSQL

**دامنه:** رفع محدودیت امنیتیِ «شمارنده IP در حافظهٔ هر API replica» پیش از اتصال واقعی پیامک. این مرحله نه ارائه‌دهندهٔ پیامک انتخاب می‌کند، نه صفحهٔ OTP فاقد طرح مصوب را نهایی می‌کند.

## کد ثبت‌شده

- جدول `identity.otp_ip_windows` با migration نسخه‌دار، کلید مرکب `partition_digest/action`، زمان شروع بازه، شمارنده و index برای پاک‌سازی؛ snapshot و تست schema نیز به‌روز شده‌اند.
- `OtpIpRateLimiter` با دستور اتمیک PostgreSQL `INSERT ... ON CONFLICT DO UPDATE ... RETURNING` سقف درخواست ۳ بار و سقف تأیید ۵ بار را **مستقل از هم و مشترک بین همه replicaها** در بازهٔ ۶۰ ثانیه‌ای از نخستین تلاش اعمال می‌کند. قفل ردیف، هم‌زمانی را سریالی می‌کند و ساعت پایگاه داده معیار است. مقادیر ۳/۵/۶۰ ثانیه پیش‌فرض فنیِ نیازمند بازبینی امنیتی‌اند، نه سیاست قطعی کسب‌وکار.
- IP از `HttpContext.Connection.RemoteIpAddress` دریافت می‌شود؛ هیچ هدر `X-Forwarded-For` ارسال‌شده توسط کاربر کورکورانه قابل‌اعتماد نیست. `IPv4-mapped IPv6` به IPv4 نرمال می‌شود و IP نامعلوم بودجهٔ محافظه‌کارانهٔ مشترک دارد. پیش از اتصال عمومی از پشت proxy باید زنجیرهٔ مورداعتماد `ForwardedHeaders`/آدرس واقعی کلاینت تنظیم و آزمایش شود؛ در غیر این صورت همهٔ کاربران ممکن است IP مشترک proxy را داشته باشند.
- خود IP به DB نوشته نمی‌شود؛ `OtpCodeCryptography.ComputeClientIpDigest` یک HMAC-SHA256 با کلید سرور و جداشده از دامنهٔ هش OTP به‌دست می‌دهد. تغییر کلید، شمارندهٔ بازه را reset می‌کند. حذف تصادفیِ ردیف‌های قدیمی (>۲۴ ساعت) با دستور پاک‌سازی و index انجام می‌شود؛ برای الزامات حریم خصوصی، backup و بازهٔ نگهداری در استقرار باید بازبینی شوند.
- در `Program.cs` middleware قبلی in-memory برداشته و محدودساز DB بعد از اعتبارسنجی شکل درخواست و بررسی آمادگی provider/DB/key، و پیش از صدور چالش یا بررسی کد اجرا می‌شود. سقف => HTTP 429؛ خطای DB => HTTP 503 و بدون ادعای ارسال/ورود. پاسخ درخواست هم `Cache-Control: no-store` دارد.
- مسیرهای `GET/DELETE /api/v1/auth/session` به provider پیامک وابسته نمی‌شوند و تغییری در ابطال نشست، کارمزد یا حساب‌های حمایت ایجاد نشده است.

## آزمون و مرز انتشار

آزمون PostgreSQL واقعی در CI: رقابت ۲۰ درخواست از DbContextهای جدا و **دقیقاً سه مجوز**، جدایی بودجهٔ `REQUEST/VERIFY` و IPها، جلوگیری از دوبرابرشدن بودجهٔ IPv4-mapped IPv6، بازنشانی با ساعت DB، نگهداری HMAC به‌جای IP خام و حذف پنجرهٔ قدیمی. migration دو بار اجرا می‌شود. بدون DB محلی تست‌های مختص PostgreSQL اجرا نمی‌شوند؛ نتیجهٔ CI با سرویس واقعی PostgreSQL معیار است.

در فایل Figma فعلی فریم‌های Auth وب و موبایل وجود دارند، اما **فریم مصوب مجزای OTP پیدا نشد**؛ بنابراین صفحه‌ای با ادعای طراحی نهایی ساخته نشده است. `UnconfiguredOtpSmsSender` در اجرای واقعی همچنان پیش‌فرض است، هیچ پیامکی از حنا ارسال نمی‌شود و OTP معتبر همچنان 503 برمی‌گردد؛ تست‌های فرستندهٔ مصنوعی فقط داخل تست‌ها هستند.

**گام بعد پس از این زیرساخت:** انتخاب و قرارداد با provider واقعی SMS، بررسی API/credential/هزینه/شناسهٔ پیگیری/وضعیت نامعلوم و سیاست idempotency/reconciliation؛ سپس adapter اختصاصی با opt-in محرمانه، اجرای E2E روی دستگاه و تکمیل طراحی OTP طبق فریم فیگمای تصویب‌شده.
