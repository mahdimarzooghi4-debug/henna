# Frontend 003 — ثبت واقعی پیش‌نویس اطلاعات اولیه فروشگاه

**دامنه:** تبدیل فرم اولیه ثبت‌نام فروشگاهِ موجود به یک مسیر ذخیره/بازیابی واقعی با PostgreSQL، بدون حدس‌زدن صفحه‌های فاقد طراحی مصوب و بدون اعلام تأیید یا فعال‌سازی فروشگاه.

## طرح مرجع

- [فریم مصوب فروشگاه وب، Figma 160:77](https://www.figma.com/design/uREafnhmH5dDRwPraBOmuk/henna-platform?node-id=160-77): شش فیلد، هدر و الگوی مرحله‌ها. فرم و کلاس‌های CSS و دارایی لوگوی موجود دوباره استفاده شدند.
- [Foundations، گره 8:4](https://www.figma.com/design/uREafnhmH5dDRwPraBOmuk/henna-platform?node-id=8-4): پالت و RTL.
- در بازبینی این مرحله، فایل Figma متصل فقط صفحهٔ «00 • Foundations» و سه فریم اجرایی auth وب (160:40)، auth اپ مصرف‌کننده (160:58)، و ثبت‌نام فروشگاه وب (160:77) داشت. فریم موبایل ثبت فروشگاه (160:111) صریحاً OUT OF SCOPE است؛ صفحهٔ خانه، فروشگاه، محصول، پرداخت، ادمین و پنل فروشنده هنوز فریم مصوب قابل‌استخراج در این فایل ندارند.

## مسیر اجرا

- `PUT /api/v1/seller/registration` با bearer معتبر و HTTPS در غیر از Development، شمارهٔ حساب **تأییدشده** و شش فیلد معتبر را در جدول `seller.registration_drafts` با کلید یکتای `account_id` ذخیره/به‌روزرسانی اتمیک می‌کند. `GET` فقط پیش‌نویس صاحب همین نشست را برمی‌گرداند.
- مهاجرت `20260920235000_InitialSellerDraft` در schema مستقل `seller` با تاریخچه migration مستقل، ستون‌های محدودشده، status فقط `DRAFT` و foreign key به حساب Identity اجرا می‌شود. دیتابیس فعلاً با connection string مشترک `IdentityDb` پیکربندی می‌شود؛ schema/model مرز جدا دارند. فرمان صریح `--apply-migrations` ابتدا Identity سپس Seller را migrate می‌کند. readiness هر دو را می‌سنجد.
- Next.js درگاه same-origin در `/api/seller/registration` است: bearer فقط از کوکی امن HttpOnly در سرور به ASP.NET منتقل می‌شود؛ کاربر مرورگر توکن نمی‌بیند. ذخیره بدون نشست 401، Origin ناهماهنگ 403، ورودی معیوب 400، شکست ناشناخته 503 و نتیجه معتبر 200 + `DRAFT` است. `Cache-Control: no-store` روی پاسخ‌هاست.
- فرم `/seller/register` روی بازدید مجدد پیش‌نویس را بازیابی می‌کند و فقط پس از پاسخ تاییدشدهٔ backend ذخیره را موفق گزارش می‌دهد. وضعیت پیش‌نویس به معنی ثبت درخواست نهایی یا فعال‌شدن فروشگاه نیست.

## مرزهای باز

- **هیچ سرویس SMS واقعی به Identity متصل نیست.** بنابراین کاربر معمولی هنوز نمی‌تواند نشست واقعی بگیرد و مسیر ذخیره برای استفادهٔ عمومی باز نیست. تست زیرساخت، دادهٔ جداگانه و تأییدشده را فقط در PostgreSQL موقت CI seed می‌کند؛ در production endpoint ساخت نشست آزمایشی وجود ندارد.
- مراحل بعدی ثبت کسب‌وکار، محدوده فعالیت، مدارک/احراز، بررسی نهایی، seller approval و seller-panel هنوز طراحی/پیاده‌سازی نشده‌اند. این مرحله فقط ثبت پیش‌نویس شش فیلد فریم موجود است.
- فیلد شمارهٔ مسئول در این مرحله باید با شمارهٔ تأییدشدهٔ حساب برابر باشد؛ افزودن مسئول با شمارهٔ مستقل نیازمند جریان اثبات مالکیت جداگانه است.
- دادهٔ ورودی فروشگاه شامل اطلاعات شخصی است؛ در پاسخ‌های خطا و لاگ برنامه نمایش داده نمی‌شود و برنامهٔ نگهداری/حذف داده قبل از انتشار عمومی باید مصوب شود.

## آزمون‌ها

GitHub Actions: `dotnet test` برای نرمال‌سازی شماره و کدپستی و اعتبارسنجی اندازه/ورودی، migration و unique draft/update در PostgreSQL واقعی، `dotnet build`، `next build`، typecheck و smoke مربوط به 401/403 در API و Next. این تست‌ها جایگزین ورود واقعی با پیامک، review بصری چندعرضی و بررسی مستندات صنفی نیستند.
