# Identity 007 — اتصال نشست بک‌اند به وب از طریق کوکی امن

**دامنه این گام:** تکمیل اتصال وب Next.js برای درخواست و بررسی OTP، نگهداری نشست سمت سرور و خروج. کد صفحه اصلی/فروشگاه یا طراحی مصوب فیگمای جدیدی ساخته نشده است. SMS واقعی هنوز متصل نیست؛ پیکربندی پیش‌فرض `UnconfiguredOtpSmsSender` باقی است و ورود عملیاتی فعال نشده.

## آنچه واقعاً ساخته شد

- مسیر `POST /api/auth/otp/request` در Next: محدودکردن درخواست به همان Origin، ورودی JSON و شماره معتبر، ارسال به `HANA_API_BASE_URL` از سرور. فقط در پاسخ **202 واقعی همراه شناسه چالش UUID معتبر** وارد مرحله کد می‌شود؛ بدون provider واقعی پاسخ 503 است.
- مسیر `POST /api/auth/otp/verify`: ورودی شماره/کد/شناسه چالش، جلوگیری از ارسال cross-origin و ارتباط server-to-server با API دات‌نت. تنها با پاسخ موفق واقعی شامل bearer، accountId و زمان انقضای معتبر، **کوکی HttpOnly + SameSite=Strict + Secure در production + Path=/** ساخته می‌شود. نام کوکی production از پیشوند `__Host-` استفاده می‌کند؛ حداکثر عمر آن مطابق نشست بک‌اند و کمتر/برابر ۲۴ ساعت است. **bearer در response JSON، URL، localStorage یا JavaScript مرورگر قرار نمی‌گیرد.**
- مسیر `GET /api/auth/session`، نشست موجود در کوکی را سرور به API ارجاع می‌دهد و فقط `authenticated/accountId` را برمی‌گرداند. نشست نامعتبر 401 و پاک‌کردن کوکی، قطعی API 503 بدون ادعای خروج است. اطلاعات حساس حساب، تلفن و نقش در پاسخ نیست.
- مسیر `DELETE /api/auth/session`، با Origin برابر origin وب، ابتدا توکن جاری را در **دیتابیس سمت ASP.NET Core** باطل می‌کند و سپس کوکی را پاک می‌کند. در وضعیت نامعلوم 503 می‌دهد و کوکی را بدون اثبات ابطال پاک نمی‌کند.
- فرم ورود موجود حالا در صورت رسیدن به 202 واقعی به مرحله ساده واردکردن کد و سپس به حالت نشست/خروج می‌رود. فرم کد صرفاً **رابط واسط فنی** است؛ صفحه/فریم OTP باید پیش از تأیید بصری با فیگما تعیین تکلیف شود، و نباید این جزئیات را «طرح مصوب» جلوه داد.

## حفاظت‌های عملیاتی

- تنها `HANA_API_BASE_URL` در پیکربندی **server-side** Next تنظیم می‌شود؛ در production فقط HTTPS قبول است. نیاز به HTTPS و تنظیم reverse proxy مورد اعتماد، Origin/Host معتبر و ملاحظات CSRF هنگام استقرار نهایی وجود دارد.
- تمام پاسخ‌های هویت و نشست `Cache-Control: no-store` دارند. اجرای تست گیت با پاسخ یک سرویس **مصنوعی صرفاً محلی در CI**، جایگزین ارائه‌دهنده SMS یا ورود کاربران واقعی نمی‌شود.
- `GET/DELETE` نشست API از مرحله 006 مستقل از قطعی SMS کار می‌کند؛ در وب، bearer تنها میان Next server و API منتقل می‌شود. در صورت سرقت session cookie، تا زمان ابطال/انقضا سوءاستفاده ممکن است؛ TLS، محافظت‌های XSS/CSRF، کلیدها و audit استقرار لازم‌اند.

## تست‌ها

GitHub Actions به‌جز ساخت/تست بک‌اند، وب و موبایل، مسیرهای 403/503/401 حالت پیش‌فرض را بررسی می‌کند. تست مستقل `tests/web-auth-gateway-smoke.mjs` فقط هنگام CI یک **سرویس TLS محلی مصنوعی** راه می‌اندازد و درخواست موفق/ناموفق را شبیه‌سازی می‌کند تا ویژگی‌های cookie، عدم افشای bearer، اعتبار نشست، رد Origin جعلی و ابطال بعد از خروج سنجیده شود؛ در shipping API هیچ fake provider ثبت نمی‌شود.

## مرحله بعد

ذخیره نشست در **Expo SecureStore** و اتصال تأیید کد اپ موبایل به `/api/v1/auth/otp/verify` با نگهداری توکن فقط در secure storage دستگاه، سپس بررسی طراحی تأییدشده کد OTP و انتخاب adapter واقعی SMS. محدودسازی IP کنونی in-memory است و پیش از انتشار باید توزیع‌شده/با اعتماد به proxy و شماره موبایل سخت‌گیری شود.
