# بک‌اند داخلی خرید حنا

وضعیت: پیاده‌سازی در شاخه توسعه، بدون ادغام یا دیپلوی. هیچ اتصال پیامک، PSP یا لجستیک افزوده نشده است.

## مسیرهای قابل فراخوانی

`POST /api/v1/commerce/commands/{action}` با Bearer session و `Idempotency-Key` از نوع UUID. کلید یکسان و ورودی یکسان، نتیجه منطقی قبلی؛ کلید یکسان و داده متفاوت، 409. هویت actor از نشست می‌آید. تمام فرمان‌های مالی/موجودی در تراکنش PostgreSQL و قفل بین پردازه‌ها انجام می‌شوند. قفل سراسری برای صحت نسخه شهر اول است؛ برای ظرفیت ملی باید به قفل منابع و load test ارتقا یابد.

| فرمان | دسترسی | کار |
|---|---|---|
| SAVE_OFFER | فروشنده فعال | قیمت و موجودی با نسخه مورد انتظار |
| SET_CART_ITEM / COMPARE_CART | خریدار | تغییر سبد و مقایسه موجودی و قیمت فروشگاه‌ها |
| SAVE_ADDRESS | صاحب نشانی | شهر مرجع و مختصات معتبر |
| CREATE_QUOTE | خریدار | پیش‌فاکتور یک فروشگاه، ۵ دقیقه اعتبار، دریافت حضوری مطابق محدوده فروشگاه |
| PLACE_ORDER | صاحب پیش‌فاکتور | بازسنجی قیمت/موجودی، مصرف اتمیک اعتبار مجاز و نقد کیف پول، تعیین مستقل KEEP/REMOVE برای اقلام ناموجود |
| CANCEL_ORDER | خریدار سفارش | لغو قبل از دریافت حضوری و بازگشت کامل به منشأ وجوه |
| SELLER_ORDER_STATE | فروشنده سفارش | پرداخت‌شده → آماده‌سازی → آماده دریافت |
| CONFIRM_PICKUP | خریدار سفارش | تأیید دریافت واقعی، زمان سرور، پایان حق لغو مستقیم |
| CREATE_PROGRAM / ALLOCATE_CREDIT | مدیر | ثبت دستور منبع و بودجه مصوب، تخصیص ΣHᵢGᵢ با فرمول پایه، سقف بودجه و گردکردن رو به پایین |
| REPORT_INCIDENT | خریدار سفارش | گزارش خرابی/کسری در یک ساعت دریافت، محدودیت تعداد و مرجع مدرک |
| DECIDE_INCIDENT | مدیر پشتیبانی | تأیید/رد با دلیل، بازپرداخت اتمیک و حفظ منشأ اعتبار |
| RETURN_CONTACT / RETURN_VISIT | فروشنده مسئول | ثبت تماس و حضور با زمان سرور و مرجع مدرک |
| CONFIRM_RETURN | خریدار | تأیید دریافت فیزیکی توسط فروشنده، بدون ادعای صوری فروشنده |
| VERIFY_UNAVAILABILITY | مدیر | معافیت مستند پس از تماس و حضور به‌موقع، بدون ساخت مراجعه مجدد |
| ASSESS_RETURN_SLA | مدیر | جریمه یک‌باره دیرکرد یک‌ساعته بر اساس مبلغ قلم سفارش |
| SET_FEE_POLICY / BUILD_SETTLEMENTS | مدیر مالی | تعرفه ثابت نسخه‌دار و مصوب، آماده‌سازی گزارش روزانه طبق روز ایران، hold پرونده‌های باز، بدون اعلام پرداخت بانکی |
| REQUEST_WITHDRAWAL / CANCEL_WITHDRAWAL | خریدار | نگهداری مبلغ نقد، مهلت ۷۲ ساعت، انتظار احراز مالکیت حساب و امکان لغو پیش از انتقال |
| OPEN_TICKET / REPLY_TICKET | صاحب تیکت / مدیر | درخواست و پاسخ پشتیبانی |

`GET /api/v1/commerce/resources/{kind}?id=...&page=1` گزارش منابع مجاز را می‌دهد. مالکیت خریدار/فروشنده در query و پیش از صفحه‌بندی اعمال می‌شود. مدیر دسترسی مدیریتی دارد. journal و receipts از مسیر عمومی ارائه نمی‌شوند.

## مرزهای مالی

- اعتبار حمایتی نقد نمی‌شود؛ LEGAL نمی‌تواند از آن استفاده کند. دسته‌های مجاز و انقضا هنگام خرید کنترل می‌شوند.
- برنامه اعتبار بر اساس اظهار مستند مدیر درباره دستور تأمین مالی ثبت می‌شود؛ API، واریز بانکی را مستقلاً تأیید نمی‌کند.
- کیف پول نقد با شارژ ساختگی یا callback فرضی پر نمی‌شود. در نبود نقد کافی و اعتبار، خرید با PAYMENT_REQUIRED_PROVIDER_UNCONFIGURED متوقف می‌شود.
- هر انتقال داخلی، journal با حساب بدهکار/بستانکار، مبلغ برابر، منشأ CASH/SUPPORT و command ثبت می‌کند. این journal به حساب‌های حقوقی/مالی مصوب و reconciliation بیرونی در مرحله اتصال نیاز دارد.
- بازپرداخت‌های جزئی از تفاضل سهم تجمعی اعتبار استفاده می‌کنند تا گردکردن باعث اضافه‌پرداخت نشود.
- تعرفه فروشگاه از سیاست مصوب مدیر دریافت می‌شود؛ تا پیکربندی آن، تسویه آماده نمی‌شود. هیچ مبلغ ۵۰۰۰ تومان hard-code نشده است.
- برداشت در انتظار احراز مالکیت حساب می‌ماند؛ مرجع درخواست احراز به معنی شبای تأییدشده نیست. پرداخت بانکی یا PAID صوری وجود ندارد.
- مأموریت ارسال، هزینه پیک و وصول بانکی در این نسخه فعال نیستند.

## اجرای دیتابیس و آزمون

`ConnectionStrings__CommerceDb` باید در محیط تنظیم شود. `--apply-commerce-migrations` یک عملیات مستقل، صریح و قابل تکرار است؛ startup معمولی دیتابیس را تغییر نمی‌دهد. داده‌های آزمون خرید در دیتابیس مجزای موقت CI ساخته می‌شوند تا کاتالوگ واقعی یا تست‌های دیگر را آلوده نکنند.

## کارهای لازم پیش از ادعای آماده‌بودن کل محصول

قراردادهای API فرمان‌ها باید به OpenAPI نهایی و مسیرهای UI/موبایل متصل شوند. تست‌های API و رقابت تراکنش‌ها، اعتبارسنجی گزارش مالی، کنترل سیاست‌های مالی باز، CMS/اعلان و دامنه سازمان، ظرفیت و وظایف زمان‌بندی باید تکمیل شوند. این فایل موفقیت بیلد یا آمادگی کل بک‌اند را پیشاپیش اعلام نمی‌کند.
