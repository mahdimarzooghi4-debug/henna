# Catalog 005 — قرارداد رسانهٔ بررسی‌شده و بک‌لاگ میزبان تصویر

## نتیجهٔ کسب‌وکار

محصول منتشرشدهٔ Catalog می‌تواند تصویر واقعی و بررسی‌شده داشته باشد تا فروشنده هنگام ساخت Offer از همان هویت و تصویر کاتالوگ استفاده کند. هویت محصول و مالکیت محتوای آن همچنان در Catalog می‌ماند؛ تصویر یا دادهٔ تجاری فروشنده نمی‌شود.

## شواهد وضعیت فعلی

- `catalog.products` و `ProductRecord` فقط هویت و وضعیت انتشار دارند؛ فیلد یا رابطهٔ تصویر وجود ندارد.
- CLI در [Catalog 004](HANA-CATALOG-004.md) فقط هویت دسته/محصول را می‌پذیرد و فیلد ناشناخته را رد می‌کند. مسیر HTTP نوشتن Catalog وجود ندارد.
- Catalog هیچ سرویس بارگذاری، مخزن باینری، تنظیم میزبان تصویر یا CDN ندارد.
- رسید import فعلی هش محتوا، زمان و شمارش ردیف را ثبت می‌کند؛ هویت اپراتور تأییدکننده یا مجوز انتشار را ثبت نمی‌کند.
- برای بازبینی ادمین، Figma مصوبی ارائه نشده است؛ UI ادمین نباید در این گام ساخته شود.

## قرارداد فنی پیشنهادی برای بررسی

این سند انتخاب ارائه‌دهندهٔ ذخیره‌سازی یا طراحی UI را انجام نمی‌دهد. برای جلوگیری از وابستگی به میزبان و واردکردن URL دلخواه، قرارداد پیشنهادی چنین است:

- فایل باینری در ذخیره‌سازی شیء پایدار نگهداری شود؛ PostgreSQL فقط شناسهٔ asset و فرادادهٔ لازم را نگه دارد.
- محصول به شناسهٔ داخلی asset متصل شود؛ URL دلخواه یا قابل‌واکشی از ورودی کاربر در Catalog ذخیره نشود. URL نمایش از میزبان/CDN صریحاً پیکربندی‌شده ساخته شود.
- Asset تا پس از بررسی اپراتور قابل نمایش عمومی نباشد. تغییر وضعیت انتشار، اتصال به محصول، تغییر/حذف فایل و هویت/زمان تصمیم باید قابل ممیزی باشد.
- فهرست فرمت‌های تصویری، سقف اندازه و ابعاد، پردازش/مشتق thumbnail، سیاست حذف و نگهداری، و مبدأهای مجاز نمایش پیش از پیاده‌سازی تصویب شوند.
- مدل Catalog باید بدون تصویر معتبر باقی بماند؛ migration هیچ تصویر یا URL ساختگی برای دادهٔ فعلی backfill نکند.
- Seller هیچ فایل یا URL تصویری بارگذاری یا تعیین نکند. وب و موبایل فقط URL عمومیِ تولیدشده از asset تأییدشده را از API Catalog بخوانند.

## وابستگی‌های باز

1. انتخاب میزبان durable object storage، مالکیت حساب، منطقهٔ میزبانی، روش اعتبارسنجی دسترسی و تأمین secret در محیط‌های stage/production.
2. انتخاب CDN یا دامنهٔ عمومی مجاز، رفتار cache و روش ساخت/چرخش URL.
3. تأیید سیاست محتوا: فرمت‌ها، سقف بایت/ابعاد، variantها، حذف، نگهداری و دسترس‌پذیری asset پس از unpublish.
4. تعیین مسیر اپراتوری تا زمان وجود Admin UI مصوب: چه نقش/فرایندی فایل را بارگذاری و چه کسی آن را تأیید می‌کند. CLI فعلی به تنهایی هویت تأییدکننده را ثابت نمی‌کند.
5. تأیید اینکه Catalog به یک تصویر اصلی در گام نخست بسنده می‌کند یا به چند تصویر با ترتیب نمایشی نیاز دارد.

تا بسته‌شدن این وابستگی‌ها، Catalog image implementation و ذخیرهٔ Seller Offer که تصویر تأییدشده می‌خواهد، شروع‌پذیر نیستند. گزینه‌های میانی مانند URL خارجی، ذخیرهٔ فایل در ریپو/دیتابیس، پوشهٔ محلی روی replica، یا تصویر placeholder پذیرفته نیستند.

## معیارهای پذیرش برای پیاده‌سازی بعدی

- فایل فقط با هویت اپراتور مجاز وارد چرخه می‌شود و وضعیت بررسی/تصمیم immutable audit دارد.
- پاسخ عمومی فقط asset تأییدشدهٔ متصل به محصول `PUBLISHED` را نشان می‌دهد؛ DRAFT/rejected/retired یا شناسهٔ ناشناخته نشت نمی‌کند.
- هیچ ورودی arbitrary URL باعث fetch سمت سرور نمی‌شود و URL نمایشی فقط از origin پیکربندی‌شده تولید می‌شود.
- خطای storage، checksum نامعتبر، فرمت ممنوع، فایل بیش‌ازحد بزرگ و retry تکراری رفتار مشخص و قابل‌آزمایش دارند.
- اتصال asset و تغییر publication اتمیک/نسخه‌دار است؛ retry هم‌کلید asset تکراری نمی‌سازد.
- تست PostgreSQL/API مسیر اپراتور، read عمومی، جداسازی وضعیت‌ها، ممیزی، و شکست/تکرار storage را می‌پوشاند؛ تست وب URLهای نامجاز را رد می‌کند.
- فقط چهار gate بک‌اند، وب، موبایل و Android ملاک CI هستند؛ iOS خارج از دامنه است.

## وضعیت

تصمیم محصولی «تصویر Catalog با بازبینی اپراتور؛ بدون upload فروشنده» ثبت شده است. این سند بک‌لاگ و قرارداد پیشنهادی را مشخص می‌کند؛ انتخاب میزبان، سیاست نگهداری و workflow مجاز اپراتور هنوز مصوب نیست. هیچ تغییر runtime یا دادهٔ تصویری اضافه نشده است.
