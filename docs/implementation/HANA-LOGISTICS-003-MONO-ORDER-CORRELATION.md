# HANA-LOGISTICS-003 — نگاشت پایدار سفارش حنا و شناسه‌های مونو

**مرحله:** Technical implementation  
**وضعیت:** مخزن هم‌بستگی و گذارهای اولیه پیاده‌سازی شده؛ dispatcher سفارش به API مونو هنوز وجود ندارد.

## دادهٔ پایدار

جدول `commerce.mono_delivery_correlations` برای هر سفارش ارسال فقط یک ردیف دارد و این مقادیر را نگه می‌دارد:

- شناسهٔ سفارش حنا؛
- کلید idempotency ثابت مشتق‌شده از شناسهٔ سفارش؛
- وضعیت محلی `PREPARED`, `REQUEST_RECEIVED` یا `MISSION_LINKED`؛
- `delivery_request_id` و `mission_id` مونو، پس از دریافت پاسخ معتبر؛
- زمان‌ها و revision برای تشخیص تغییر.

آدرس، نام و شماره تماس، اقلام بسته، Quote، بدنهٔ درخواست و payload رویدادهای بیرونی در این جدول ذخیره نمی‌شوند. شناسه‌های مونو روی هر دو ستون یکتا هستند تا یک درخواست یا مأموریت به دو سفارش حنا وصل نشود.

## رفتار retry

`PrepareAsync` فقط سفارش موجود با `FulfillmentMode=DELIVERY` را می‌پذیرد و کلید ثابت `henna-delivery-{order-guid}` را برمی‌گرداند. فراخوانی دوباره همان کلید و همان ردیف را می‌دهد. اگر پاسخ POST مونو به‌علت timeout نامعلوم بماند، dispatcher آینده باید همان کلید را برای تکرار همان بدنه استفاده کند. مونو درخواست دقیقاً تکراری را replay می‌کند؛ بدنهٔ متفاوت با همان کلید باید خطای تعارض محسوب شود.

گذار به `REQUEST_RECEIVED` فقط پس از پاسخ مونو با `status=RECEIVED` مجاز است. این وضعیت پذیرش یا ایجاد مأموریت نیست. شناسهٔ مأموریت فقط پس از مشاهدهٔ آن در پاسخ خواندنی مونو به `MISSION_LINKED` نگاشت می‌شود؛ وضعیت مأموریت به وضعیت تجاری سفارش حنا تبدیل نمی‌شود.

## محدوده و آزمون

- این بخش هیچ درخواست شبکه‌ای ارسال نمی‌کند و checkout فعلی حنا همچنان فقط `PICKUP` است.
- شاخهٔ آماده‌سازی فقط شناسه‌ها را ذخیره می‌کند؛ payload حمل باید در dispatcher از سفارش/دادهٔ معتبر دوباره ساخته شود.
- تست PostgreSQL مهاجرت، کلید ثابت، replay، اتصال شناسه‌ها، جلوگیری از اتصال یک شناسه به چند سفارش و رد سفارش حضوری را می‌سنجد.
- این پیاده‌سازی به معنی آماده‌بودن sandbox، API key، بسته‌بندی، نگاشت شعبه، Quote معتبر یا webhook نیست.
