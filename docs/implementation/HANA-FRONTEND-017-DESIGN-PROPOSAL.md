# Frontend 017 — پیش‌نویس طراحی جزئیات کالا/خدمت خریدار، وب و Expo

**وضعیت تاریخی در Frontend 017:** DESIGN PROPOSAL — NOT APPROVED — NOT IMPLEMENTED (زمان ساخت). **به‌روزرسانی Frontend 018:** مالک در پاسخ صریح «بله تایید میکنم» هر شش فریم جزئیات را تأیید کرد و سپس وب و Expo بر همان مبنا پیاده‌سازی شدند؛ برچسب‌های DRAFT در بوم سابقهٔ طرح اولیه هستند. تأیید خانهٔ خریدار به‌تنهایی تأیید جزئیات محسوب نشده بود.

تمام فریم‌ها در زمان ایجاد `DRAFT / NOT APPROVED` نام‌گذاری و در خود طرح نیز با برچسب مشخص شده‌اند؛ این برچسب‌ها هنوز در بوم، سابقهٔ تأییدِ بعدی مالک را منعکس نمی‌کنند. لوگوی حنا از فریم‌های خانهٔ خریدار، فونت Vazirmatn و رنگ‌های Foundations (`#F7F3ED`, `#0F5B5A`, `#B5523B`, `#D7B895`) استفاده شده است. نام‌های «عنوان کالا یا خدمت از API» **صرفاً placeholder صریح طراحی** هستند، نه نام کالای ساختگی، دادهٔ seed یا وعدهٔ محتوای تولیدی.

در صفحهٔ `01 • Buyer Journey` فریم‌های قدیمی `APP / 02 Product Detail` (`227:123`)، `WEB / 02 Product Detail` (`227:1262`) و `mobile-product-detail` (`452:930`) وجود دارند، اما شامل قیمت، عکس، تعداد، موجودی یا سبد هستند و **مبنای مجازِ پیاده‌سازی API فعلی نیستند**. این شش فریم جدید پیشنهاد محدود به قرارداد واقعی‌اند و جای آن‌ها را بی‌سروصدا عوض نکرده‌اند.

## منبع داده و مرز API

در وب `GET /api/catalog/products/{id}` از BFF فعلی Next به `GET /api/v1/catalog/products/{id}` ASP.NET می‌رسد. در Expo متد `MobileCatalogClient.detail(id)` همین API عمومی را به‌صورت بدون نشست می‌خواند. فقط محتوای published که دستهٔ published داشته باشد با `id`, `categoryId`, `name`, `kind=GOOD|SERVICE`, `description: string|null` برمی‌گردد. `categoryId` **شناسه** است نه نام دسته؛ نام دسته در این پاسخ تضمین نمی‌شود. `description=null` یعنی بخش توضیح نمایش داده نشود.

- ۲۰۰ معتبر → کارت متنی عنوان، نوع، توضیح اختیاری و ارجاع دسته طبق دادهٔ واقعی، بدون نمونهٔ تجاری.
- ۴۰۴ واقعی → «پیدا نشد» و بازگشت به فهرست؛ نه کالای نمونه، نه اطلاعات ذخیره‌شدهٔ محصول قبلی.
- ۵۰۳، قطع شبکه، timeout، response نامعتبر یا ناسازگاری شناسهٔ پاسخ با شناسهٔ خواسته‌شده → «دریافت جزئیات تأیید نشد» با تلاش دوباره + بازگشت؛ **به‌اشتباه ۴۰۴ نشود**.
- شناسهٔ malformed/empty به API درخواست نزنَد. مطابق قرارداد موجود BFF وب این مورد را ۴۰۴ و کلاینت موبایل `invalid` می‌نامد؛ در UI نباید دادهٔ قبلی برای آن نمایش داده شود.
- هنگام بازکردن محصول دیگر، خروج از صفحه و بازگشت، درخواست قبلی باید لغو/بی‌اثر شود. نتیجهٔ جدید فقط پس از تطبیق ID با مسیر/انتخاب جاری نشان داده شود.
- بازگشت به مرور کاتالوگ حفظ جست‌وجو/فیلتر/صفحه را **در صورت تصمیم اجرایی** بهتر می‌کند؛ نیازمند تثبیت قرارداد navigation است و این سند آن را پیاده‌شده معرفی نمی‌کند.

**عمداً خارج از طراحی و انتشار:** قیمت، تخفیف، تصویر محصول، وزن یا مشخصات ناموجود در DTO، فروشندهٔ تأییدشده، موجودی، آمادگی شهر، زمان تحویل، تعداد، سبد خرید، checkout و پرداخت. مسیر جزئیات، کلیک کارت‌های فهرست، native screen و تست‌های جدید در این PR نوشته نشده‌اند.

## معیارهای پذیرش پیشنهادی مرحلهٔ اجرایی پس از تأیید مالک

پیاده‌سازی وب و Expo بر اساس همین شش فریم، حفظ navigation قابل‌دسترس از کارت واقعی محصول به جزئیات و برگشت به فهرست، آزمون معتبر بودن شناسه/پاسخ و جلوگیری از نشت فیلدهای خصوصی، تفکیک ۲۰۰/۴۰۴/۵۰۳ و race cancellation، آزمون مرورگر واقعی وب و آزمون client/controller موبایل با دادهٔ CI-only. انطباق تصویر موبایل روی دستگاه هنوز نیازمند آزمون جداست.

**تصمیم مالک گرفته شد:** هر شش فریم `480:2–480:7` صریحاً تأیید شدند. جزئیات اجرای وب/Expo و CI در [Frontend 018](HANA-FRONTEND-018.md) ثبت شده‌اند؛ Frontend 017 همچنان سند تحویل طراحی تاریخی است.
