# ماتریس آزمون پذیرش کسری/خرابی، جمع‌آوری و تسویه — ۰.۱

**هدف:** پیاده‌سازی و QA فنی ADR-019 تا ADR-037 پیش از انتشار عمومی شهر اول، بدون پاسخ‌خواهی مجدد به تصمیم‌های تصویب‌شده.  
**مرجع:** [طراحی جریان](../architecture/HANA-INCIDENT-REFUND-SETTLEMENT-TECHNICAL-DESIGN-v0.1.md) و [قرارداد پیشنهادی API](../api/HANA-INCIDENT-SETTLEMENT-API-CONTRACT-v0.1.md).  
**قاعده:** داده‌های نمونه ریال و زمان UTC هستند. هر مورد باید در integration و سناریوهای مهم از دو دید buyer/seller/support/finance در E2E اجرا شود؛ این سند «تست اجراشده» نیست.

| ID | ورودی/رخداد | انتظار |
|---|---|---|

| B06 | جبران خرابی ۸۰۰٬۰۰۰ ریال cash | ۸۰۰٬۰۰۰ به موجودی **قابل‌استرداد** کیف پول؛ نه bank auto payout |

| B08 | retry تأیید پشتیبانی و outbox | یک refund/یک hold بازپس‌گیری، بدون double credit |

| B10 | وضعیت refund موفق، کالای خراب هنوز نزد مشتری | refund پابرجا؛ collection شرط نیست |

| D11 | retry تأیید عدم دسترسی | یک تصمیم و یک آزادسازی، بدون جریمه یا وظیفه دوم |

## E. تسویه، جریمه، retry و حسابرسی

| ID | ورودی/رخداد | انتظار |
|---|---|---|
| E01 | hold هنگام اجرای payout همان فاکتور وجود دارد | worker حق submit پرداخت ندارد؛ وضعیت PAID دروغی ممنوع |
| E02 | هم‌زمان گزارش معتبر و payout submit | روی یک fence/lock serial؛ **پس از hold فعال** پرداخت رخ ندهد |
| E03 | سفارش دیگری از همان فروشگاه hold ندارد | hold فاکتور اول، پرداخت فاکتور دوم را بی‌دلیل متوقف نکند |
| E04 | کالای خراب قیمت فهرست ۱۰۰٬۰۰۰ و قیمت واقعی سفارش ۸۰٬۰۰۰ ریال است | جریمه **۸۰٬۰۰۰** برای واحد آسیب‌دیده، نه قیمت فهرست/کل سفارش |
| E05 | پرداخت نقدی/اعتباری ترکیبی برای یک قلم | قیمت کالا با «فقط مبلغ cash» اشتباه نشود |
| E06 | تأیید عدم دسترسی مشتری با تماس+مراجعه در مهلت | **هیچ** ردیف جریمه در تسویه آن پرونده نباشد |
| E07 | تخلف تأییدشده، callback تکراری | تنها یک `SELLER_PENALTY` و یک `SETTLEMENT_DEDUCTION` |
| E08 | مبلغ سهم حمل و جریمه هم‌زمان کسر می‌شوند | دو ردیف مستقل با مراجع مجزا و net قابل تطبیق |
| E09 | refund قبلاً به مشتری رفته، فروشگاه بعداً جریمه می‌شود | wallet دوباره بستانکار نشود؛ جریمه متعلق به حساب فروشنده |
| E10 | رفع hold در میانه روز کاری ساعت ۱۲:۲۰ | payout فوری میان‌روزی ساخته نشود؛ فاکتور به چرخه تسویه پایان همان روز کاری یا چرخه واجد شرایط بعدی بازگردد |
| E11 | پایان روز کاری حنا، همه holdهای فاکتور رفع و اصلاحات مالی ثبت شده | فاکتور مجاز در چرخه روزانه قابل submit با idempotency و reconciliation باشد |
| E12 | payout موفق **قبل** از ثبت گزارش، یا net بعد از کسورات ناکافی است | بدهی carry-forward/منفی/برداشت خودکار بدون ADR جدید فرض نشود؛ queue رسیدگی مالی |
| E13 | timeout PSP/بانک در payout | وضعیت UNKNOWN/PENDING و reconcile، نه PAID فرضی یا submit دوباره کور |
| E14 | دو پرونده بر اقلام/تعداد یکسان همپوشان‌اند | مانع جبران/penalty دوباره؛ تعیین مبلغ دقیق تخفیف سبدی تا تصویب policy باز |
| E15 | پایان روز کاری؛ فروشگاه الف فاکتور A held و B مجاز، فروشگاه ب فاکتور C مجاز دارد | B و C به چرخه تسویه وارد شوند؛ A تا رفع hold پرداخت نشود |
| E16 | اجرای تکراری batch پایان روز کاری و callback تکراری پرداخت | برای هر مبلغ فقط یک payout/ledger، وضعیت بانکی نامعلوم با PAID اشتباه نشود |
| E17 | فاکتور تا بعد از بسته‌شدن چرخه روزانه held، سپس آزاد می‌شود | payout میان‌روزی صوری نباشد؛ ورود به چرخه روز کاری واجد شرایط بعدی |

## گیت آماده‌بودن

- اجرای خودکار سناریوهای A–F و گزارش evidence در CI / staging لازم است؛ «تست نشده» معادل «پاس شده» نیست.
- قبل از انتشار: contract نهایی/OpenAPI، migration با unique constraints، outbox/inbox، runbook hold مانده، دسترسی tenant، تطبیق wallet و فروشگاه، تست concurrency و تست بازیابی سرور.
- سیاست‌های باز: روش اثبات حضور، تخفیف سبدی/همپوشانی دقیق، وضعیت payout قبلی و کسری net و تقویم/ساعت دقیق پایان روز کاری تسویه همه فروشگاه‌ها طبق ADR-038؛ این‌ها باید **صریحاً** در release gate بررسی شوند و پیش‌فرض دلخواه جایگزین تصمیم محصول نشود.
